# R-1 — File grandi su mobile

> **Stato: PENDING** — in attesa di esecuzione su dispositivi reali. Prototipo costruito e type-checked, non ancora eseguito in Obsidian.

## Domanda

Le API di Obsidian `readBinary`/`writeBinary` lavorano su file interi in memoria. Su iPhone e Android reali, un file da 50/200/500 MB si riesce a leggere, hashare (SHA-256 incrementale), caricare a chunk da 4 MiB e riscrivere? Quanta memoria e quanto tempo servono? Esistono API utilizzabili per **lettura parziale** o **scrittura in append** che evitino di tenere il file intero in memoria?

## Ipotesi e criterio di successo

- **Ipotesi:** su desktop tutto funziona fino a 500 MB; su mobile la pipeline "tutto in memoria" fallisce o diventa instabile oltre una certa soglia (presumibilmente tra 200 e 500 MB, prima su iOS).
- **Ipotesi alternativa da verificare:** l'URL della risorsa (`adapter.getResourcePath`) letto con `fetch` permette lettura in streaming e/o con header `Range`, e `adapter.appendBinary` (Obsidian ≥ 1.12.3) permette scritture a chunk: insieme renderebbero la memoria indipendente dalla dimensione del file.
- **Successo:** per ogni piattaforma si ricava un **limite effettivo** (dimensione massima gestita senza crash con margine) e si sa se la pipeline in streaming è praticabile.
- **Se fallisce** (da §10): limite effettivo per mobile più basso (es. 100 MB); i file sopra soglia sono sincronizzati solo dai desktop e mostrati come "solo desktop" sui dispositivi mobili.

## Setup

- Dispositivi: iPhone, telefono Android, un desktop (riferimento). Annotare modello, RAM se nota, versione del sistema operativo, versione di Obsidian.
- Obsidian ≥ 1.12.3 (il manifest lo richiede per `appendBinary`).
- Vault di prova in memoria locale, plugin di spike installato, server di prova avviato: vedi [setup comune](README.md#setup-comune).
- Spazio libero sul dispositivo: almeno 1,5 GB (file da 500 MB + copia temporanea).
- I comandi lavorano nella cartella del vault **`kamino-spike-large/`**.

## Procedura passo-passo

Ripetere su ogni dispositivo. Chiudere le altre app prima di iniziare; tenere il telefono sbloccato e Obsidian in primo piano durante ogni comando.

1. **Sonda delle API** — comando `R-1: probe adapter APIs (append/appendBinary/range read)`. Elenca i metodi dell'adapter, verifica `appendBinary` su un file da 2 MiB, prova `fetch` dell'URL della risorsa con `Range: bytes=…` e in streaming (`response.body.getReader()`). Nessun file grande coinvolto.
2. **Generazione dei file di prova** — comando `R-1: generate a test file (50/200/500 MB)`, scegliere 50, poi 200, poi 500. Il file viene scritto a pezzi da 4 MiB (`writeBinary` + `appendBinary`), quindi la generazione non richiede il file intero in memoria.
   - Se la generazione fallisce (es. `appendBinary` assente), creare i file sul computer e copiarli in `kamino-spike-large/` con lo stesso metodo usato per il plugin:
     - Git Bash / macOS / Linux: `head -c 52428800 /dev/urandom > test-50mb.bin` (200 MB = `209715200`, 500 MB = `524288000`);
     - PowerShell: `$b = [byte[]]::new(52428800); [Random]::new().NextBytes($b); [IO.File]::WriteAllBytes("$PWD\test-50mb.bin", $b)`.
3. **Pipeline "tutto in memoria"** — comando `R-1: full-memory pipeline (readBinary, hash, upload, writeBinary)`, scegliere il file da 50 MB. Esegue in sequenza: `readBinary`, SHA-256 incrementale con `@noble/hashes` (aggiornamenti da 4 MiB), upload a chunk da 4 MiB con `requestUrl` verso il server di prova (che risponde con il proprio SHA-256), `writeBinary` di una copia (poi cancellata). Attendere l'avviso finale. Ripetere con 200 MB e poi 500 MB.
   - Se l'app si chiude o si blocca: annotarlo, riaprire Obsidian, aprire l'ultima nota `R-1 …` e registrare l'ultima riga presente (= ultimo passo riuscito). Controllare anche il log del server.
4. **Pipeline in streaming** — comando `R-1: streaming pipeline (resource URL, hash, upload, appendBinary)` su 50, 200, 500 MB. Legge con `fetch(getResourcePath(...))` in streaming, accumula chunk da 4 MiB, li hasha, li carica e li scrive in append su una copia (poi cancellata).
5. Su **desktop** ripetere i passi 1–4 come riferimento.
6. Pulizia: comando `R-1: delete the large test files`.

## Impatto su ADR/requisiti

- **Streaming funziona su entrambe le piattaforme** (lettura in streaming o con `Range` + `appendBinary`): nessun limite rigido lato mobile; il plugin adotta la pipeline in streaming per i file sopra una soglia (da fissare) e `readBinary`/`writeBinary` sotto. `minAppVersion` del plugin va portato almeno a 1.12.3. Da riflettere in `03-sync-protocol.md` (upload a chunk) senza nuova ADR, salvo cambi di protocollo.
- **Streaming funziona solo in lettura** (manca `appendBinary` o è inaffidabile): upload senza limite, download limitato dalla memoria → limite effettivo per i download su mobile, file oltre soglia marcati "solo desktop" in ricezione.
- **Nessuna alternativa praticabile:** si applica il fallback di §10: limite per mobile pari alla dimensione più grande gestita senza crash con margine (es. 100 MB), file sopra soglia "solo desktop". Va aggiunto come requisito esplicito in `01-requirements.md` e reso visibile nella UI (promessa "sai sempre se sei al sicuro"); valutare una ADR se il limite cambia il modello dei dati (stato "solo desktop" per file).
- **Desktop:** se anche il desktop fallisce a 500 MB con la pipeline in memoria, la pipeline in streaming diventa obbligatoria anche lì.
